## 一、选型原则

| 原则 | 说明 |
|------|------|
| **成熟稳定** | 优先选择业界广泛使用、社区活跃的技术 |
| **团队熟悉度** | 考虑团队成员现有技能栈，降低学习成本 |
| **课程契合度** | 技术栈与课程教学内容匹配，最大化学习价值 |
| **可扩展性** | 技术方案需支持第二阶段AI/区块链功能扩展 |
| **免费/开源** | 不依赖付费服务，学生团队可自主掌控 |

## 二、后端技术选型

### 2.1 核心框架：Spring Boot 3.x

| 维度 | 评估 |
|------|------|
| **选择理由** | Java生态最主流的微服务框架，团队成员课程重点学习内容 |
| **社区活跃度** | GitHub 74k+ Stars，生态丰富 |
| **学习曲线** | 中等，团队成员已具备基础 |
| **替代方案** | Node.js/Express（性能好但生态碎片化）、Python/Django（不适合高并发场景） |

**选型结论**：Spring Boot 3.x 是企业级应用的事实标准，与课程教学高度契合，不作为降级选项。

### 2.2 ORM框架：MyBatis-Plus

| 维度 | 评估 |
|------|------|
| **选择理由** | 在MyBatis基础上增强，支持Lambda查询、自动分页、逻辑删除等 |
| **vs MyBatis** | MyBatis-Plus内置CRUD，减少90%的简单SQL编写 |
| **vs JPA/Hibernate** | MyBatis-Plus对复杂SQL更友好，学习成本更低 |
| **替代方案** | JPA（自动建表但复杂查询弱）、JOOQ（类型安全但学习成本高） |

**选型结论**：MyBatis-Plus，兼顾开发效率和SQL灵活性。

### 2.3 安全框架：Spring Security + JWT

| 维度 | 评估 |
|------|------|
| **选择理由** | 与Spring Boot深度集成，支持自定义认证Provider扩展 |
| **认证方式** | JWT无状态Token + 注册时校园网IP检测 |
| **vs Shiro** | Spring Security功能更全面，与Spring生态集成更好 |
| **替代方案** | Apache Shiro（轻量但扩展性弱）、Sa-Token（国产但社区较小） |

**选型结论**：Spring Security + JWT，注册时检测校园网IP，登录无需IP检测。

### 2.4 接口文档：Knife4j

| 维度 | 评估 |
|------|------|
| **选择理由** | Spring Boot的Swagger增强工具，支持中文、离线文档、在线调试 |
| **vs SpringDoc** | Knife4j在SpringDoc基础上提供更好的UI和体验 |
| **替代方案** | YApi（需要额外部署）、Postman（手动维护） |

**选型结论**：Knife4j，一行依赖即可自动生成接口文档。

### 2.5 数据库：MySQL 8.0

| 维度 | 评估 |
|------|------|
| **选择理由** | 最主流的关系型数据库，课程必学 |
| **vs PostgreSQL** | MySQL在国内使用率更高，文档和中文资源更多 |
| **必要特性** | 全文索引（商品搜索）、JSON字段（灵活扩展）、窗口函数 |

**选型结论**：MySQL 8.0。

### 2.6 缓存：Redis 7.x

| 维度 | 评估 |
|------|------|
| **选择理由** | 缓存热点数据、Session管理、Token黑名单 |
| **初期使用场景** | 分类数据缓存、用户Session、Token失效列表 |
| **后期扩展** | 消息队列（Stream）、分布式锁、排行榜 |

**选型结论**：Redis 7.x，轻量实用。

### 2.7 AI推荐服务：Python Flask + scikit-learn

| 维度 | 评估 |
|------|------|
| **选择理由** | Python拥有最成熟的机器学习/推荐算法生态，Flask轻量适合微服务 |
| **vs Java ML** | Java的ML库（如Mahout）远不如Python生态成熟和易用 |
| **vs 外部API** | 自建推荐服务避免外部API费用和数据隐私问题 |
| **核心算法** | 初期使用协同过滤（UserCF + ItemCF），冷启动使用热门+分类兜底 |
| **替代方案** | TensorFlow（过重）、PyTorch（过重）、Surprise（单纯推荐库，可考虑） |

**选型结论**：Flask + scikit-learn，独立HTTP微服务，通过REST API与后端通信。

### 2.9 消息队列：RabbitMQ 3.12+

| 维度 | 评估 |
|------|------|
| **选择理由** | 实现单体内部业务解耦与异步化，支持消息的可靠投递与延时状态机控制 |
| **核心场景** | 用户行为日志异步上报、订单15分钟未支付/未确认延时自动取消 |
| **选择 RabbitMQ** | 相比 Redis List，提供了可靠的 ACK 机制、死信队列及延时队列插件 |

**选型结论**：RabbitMQ 3.12+。

### 2.10 文件存储：本地 → MinIO/OSS（前端直传+签名）

| 维度 | 评估 |
|------|------|
| **选择理由** | MVP 阶段使用本地文件系统，后期迁移到 MinIO 对象存储或公网 OSS |
| **优化设计** | 引入“前端直传 + 后端签名授权”模式，绕过 Java 服务器网卡带宽占用瓶颈 |
| **抽象封装** | 抽象 FileService 接口，支持本地存储与 MinIO/OSS 接口的无缝切换 |

**选型结论**：FileService 接口抽象 + 前端直传 + MinIO（后期）。

### 2.11 分库分表与读写分离：ShardingSphere-JDBC 5.x

| 维度 | 评估 |
|------|------|
| **选择理由** | 单体架构内嵌式分库分表组件，解决行为埋点表单表数据过大的读写性能瓶颈 |
| **Sharding 策略** | 用户行为埋点表（user_behavior）按照 user_id 进行 Hash 分表（4个分表） |
| **读写分离** | 自动拦截读写 SQL，配置主库写、从库读，分担数据库并发读写负载 |

**选型结论**：ShardingSphere-JDBC 5.x。

### 2.12 分布式定时任务：XXL-JOB 2.4+

| 维度 | 评估 |
|------|------|
| **选择理由** | 国内最主流的分布式任务调度平台，解决单体集群部署下任务重复执行问题 |
| **应用场景** | 毕业生清仓特卖到期自动恢复原价、租赁合同逾期自动扣减信用分 |
| **vs Spring Scheduled** | 提供可视化控制台，支持分片广播、故障转移与动态触发周期修改 |

**选型结论**：XXL-JOB 2.4+。

### 2.13 规则引擎：Aviator 5.x

| 维度 | 评估 |
|------|------|
| **选择理由** | 高性能、轻量级的 Java 表达式引擎，用于解耦变动频繁的业务计算逻辑 |
| **应用场景** | 商品 AI 折旧估价计算公式、用户信用分奖惩变动规则 |
| **解耦优势** | 规则配置于数据库，热加载运行，无需因为规则微调而重新打包部署单体 |

**选型结论**：Aviator 5.x。

### 2.14 本地一级缓存：Caffeine Cache

| 维度 | 评估 |
|------|------|
| **选择理由** | 性能最强的 JVM 进程内本地缓存，用于构建多级（三级）缓存架构 |
| **应用场景** | 商品分类树、静态配置等高频查询、低频更新的热点数据 |
| **同步失效** | 当数据更新时，通过 RabbitMQ 广播通知各单体节点同步清除 Caffeine 本地缓存 |

**选型结论**：Caffeine Cache。

### 2.15 流量防卫兵：Sentinel Standalone

| 维度 | 评估 |
|------|------|
| **选择理由** | 轻量级、功能强大的单机流量防护组件，保障单体对外 API 安全 |
| **核心功能** | 针对发帖/岗位申请接口限流防刷，对 Python 推荐接口配置熔断降级 |
| **vs 自定义限流** | 提供了丰富度高的系统自适应防护、滑动窗口限流和故障熔断能力 |

**选型结论**：Sentinel Standalone。

### 2.16 实时推送长连接：WebSocket

| 维度 | 评估 |
|------|------|
| **选择理由** | 提供全双工实时双向通信，为第二阶段无缝引入买卖双方 IM 聊天奠定基础 |
| **应用场景** | 协商出价通知、换物状态提醒、小法庭陪审团投票实时同步 |
| **集群路由** | 结合 RabbitMQ 广播机制，实现分布式多实例部署下的 WebSocket 消息路由 |

**选型结论**：WebSocket 协议。

## 三、前端技术选型

### 3.1 核心框架：Vue 3

| 维度 | 评估 |
|------|------|
| **选择理由** | 团队成员课程主学Vue，学习曲线平缓，中文文档完善 |
| **vs React** | Vue上手更快，适合团队项目，Composition API与React Hooks相似 |
| **替代方案** | React（生态大但学习陡峭）、Angular（过重） |

**选型结论**：Vue 3 + Composition API。

### 3.2 构建工具：Vite 5.x

| 维度 | 评估 |
|------|------|
| **选择理由** | Vue官方推荐，秒级热更新，开发体验极好 |
| **vs Webpack** | Vite开发服务器启动速度比Webpack快10倍以上 |
| **替代方案** | Webpack（配置复杂，打包慢）、Turbopack（不成熟） |

**选型结论**：Vite 5.x，Vue 3的标准构建工具。

### 3.3 UI组件库：Element Plus 2.x

| 维度 | 评估 |
|------|------|
| **选择理由** | Vue 3生态最成熟的组件库，中文文档，与校园项目风格匹配 |
| **vs Ant Design Vue** | Element Plus更轻量，中文社区更大 |
| **vs Naive UI** | Naive UI较新，Element Plus稳定性更好 |
| **替代方案** | Ant Design Vue（功能多但略重）、Naive UI（好看但生态小） |

**选型结论**：Element Plus，组件齐全、文档完善。

### 3.4 状态管理：Pinia 2.x

| 维度 | 评估 |
|------|------|
| **选择理由** | Vue 3官方推荐，TypeScript支持好，API简洁 |
| **vs Vuex 4** | Pinia是Vuex 5的替代品，Vue官方推荐迁移到Pinia |
| **替代方案** | Vuex（旧项目多，但已不推荐新项目使用） |

**选型结论**：Pinia 2.x。

### 3.5 HTTP客户端：Axios 1.x

| 维度 | 评估 |
|------|------|
| **选择理由** | 最流行的HTTP库，拦截器机制，请求/响应转换 |
| **vs Fetch API** | Axios自动JSON转换、超时设置、拦截器更便捷 |
| **替代方案** | Fetch（原生但有兼容问题）、ofetch（较新） |

**选型结论**：Axios 1.x。

### 3.6 路由：Vue Router 4.x

| 维度 | 评估 |
|------|------|
| **选择理由** | Vue 3官方路由库，支持路由守卫、懒加载 |
| **替代方案** | 无合理替代，这是唯一选择 |

**选型结论**：Vue Router 4.x。

## 四、工具链选型

### 4.1 版本控制：Git + GitHub/GitLab

| 维度 | 评估 |
|------|------|
| **选择理由** | 业界标准，免费私有仓库（GitHub Student Pack） |
| **vs SVN** | Git分布式，分支管理更灵活 |

**选型结论**：Git + GitHub（或学校自建GitLab）。

### 4.2 构建工具：Maven（后端）

| 维度 | 评估 |
|------|------|
| **选择理由** | Java生态标准构建工具，课程教学使用，IDEA深度集成 |
| **vs Gradle** | Maven配置更简单，xml格式团队更熟悉 |

**选型结论**：Maven 3.8+。

### 4.3 包管理：npm/pnpm（前端）

| 维度 | 评估 |
|------|------|
| **选择理由** | pnpm更快更省磁盘，npm为Node.js自带 |
| **推荐** | 优先使用pnpm（需额外安装），备选npm |

**选型结论**：npm（默认）/ pnpm（推荐）。
