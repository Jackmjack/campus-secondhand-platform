## 二、Git Flow 分支模型

### 2.1 分支架构

```
main (生产分支)
  │
  ├── develop (开发主分支)
  │     │
  │     ├── feature/auth-ip-register       (功能分支)
  │     ├── feature/product-crud         (功能分支)
  │     ├── feature/search-filter        (功能分支)
  │     ├── feature/order-negotiation    (功能分支)
  │     ├── feature/user-review          (功能分支)
  │     └── feature/frontend-xxx         (前端功能分支)
  │
  └── hotfix/xxx  (紧急修复分支，从main分出)
```

### 2.2 分支类型说明

| 分支类型 | 命名格式 | 来源 | 合并到 | 用途 |
|----------|----------|------|--------|------|
| `main` | - | - | - | 生产就绪代码，只接受来自develop和hotfix的PR |
| `develop` | - | - | - | 开发主线，最新开发代码的集成分支 |
| `feature/*` | `feature/模块名-功能简述` | `develop` | `develop` | 新功能开发 |
| `hotfix/*` | `hotfix/问题简述` | `main` | `main` + `develop` | 生产环境紧急修复 |

### 2.3 分支生命周期

```
1. 从develop创建feature分支
   git checkout -b feature/auth-ip-register develop

2. 在feature分支上开发+提交
   git add .
   git commit -m "[auth] 实现校园网IP检测注册接口"

3. 推送到远程
   git push origin feature/auth-ip-register

4. 创建Pull Request → develop
   (在GitHub/GitLab上操作)

5. Code Review通过后合并
   (由A或另一位成员Review)

6. 删除feature分支
   git branch -d feature/auth-ip-register
   git push origin --delete feature/auth-ip-register
```

## 四、Git工作流（日常操作）

### 4.1 每日开始工作前

```bash
# 1. 切换到develop分支
git checkout develop

# 2. 拉取最新代码
git pull origin develop

# 3. 基于最新develop创建feature分支（如果是新功能）
git checkout -b feature/xxx develop
```

### 4.2 开发过程中

```bash
# 频繁小步提交，每完成一个小功能点就提交
git add .
git commit -m "[模块] 简短描述"

# 每天结束时推送到远程（防止本地丢失）
git push origin feature/xxx
```

### 4.3 提交信息格式

```
[模块标签] 简短描述（50字以内）

可选详细说明（72字换行）

关联Issue: #123
```

**模块标签**：

| 标签 | 含义 |
|------|------|
| `[auth]` | 认证模块 |
| `[product]` | 二手商品模块 |
| `[order]` | 订单模块 |
| `[review]` | 评价模块 |
| `[user]` | 用户模块 |
| `[search]` | 搜索模块 |
| `[recommend]` | AI推荐模块 |
| `[forum]` | 论坛模块 |
| `[barter]` | 以物换物模块 |
| `[rental]` | 租赁模块 |
| `[clearance]` | 清仓打折模块 |
| `[cardshare]` | 拼卡共享模块 |
| `[job]` | 兼职副业模块 |
| `[groupbuy]` | 拼团模块 |
| `[court]` | 小法庭模块 |
| `[frontend]` | 前端通用 |
| `[config]` | 配置变更 |
| `[docs]` | 文档变更 |
| `[deploy]` | 部署相关 |
| `[fix]` | Bug修复 |

**示例**：
```

- 支持多图上传（最多9张）
- 图片自动压缩(>1MB时)
- 首图自动设为封面图
- 使用本地文件存储，预留OSS接口

关联Issue: #7
```

### 4.4 合并前操作

```bash
# 1. 确保feature分支包含develop的最新代码
git checkout develop
git pull origin develop
git checkout feature/xxx
git merge develop

# 2. 解决冲突（如果有）

# 3. 推送并创建PR
git push origin feature/xxx
# 然后在GitHub/GitLab上创建Pull Request
```

## 五、Code Review流程

### 5.1 PR要求

| 要求 | 说明 |
|------|------|
| 标题 | 清晰描述做了什么 |
| 描述 | 列出变更内容、测试情况、截图（如有UI变更） |
| 关联Issue | `Closes #123` |
| Reviewer | 至少1人（前后端交叉Review） |
| 合并方式 | **Squash and Merge**（将多个提交压缩为一个） |

### 5.2 PR模板

```markdown
## 变更描述
简述本次变更做了什么

## 变更类型
- [ ] 新功能
- [ ] Bug修复
- [ ] 重构
- [ ] 文档
- [ ] 配置

## 测试情况
- [ ] 本地测试通过
- [ ] 接口测试通过（后端）
- [ ] UI验收通过（前端）

## 截图（如有UI变更）
（粘贴截图）

## 关联Issue
Closes #XXX
```

### 5.3 Review检查清单

- [ ] 代码符合规范（见《代码规范文档》）
- [ ] 没有硬编码的配置（密码、IP等）
- [ ] 异常处理完整（没有空的catch块）
- [ ] 日志记录合理（不含敏感信息）
- [ ] 数据库变更有对应的SQL脚本
- [ ] 前端有loading和empty状态处理

## 六、冲突解决

### 6.1 冲突预防

1. **小步提交**：不要憋一天才提交一次
2. **每日同步**：每天开始前 `git pull origin develop`
3. **控制范围**：一个feature分支只做一件事
4. **及时合并**：feature分支存活不超过3天

### 6.2 解决冲突步骤

```bash
# 解决冲突
git checkout develop && git pull
git checkout feature/xxx
git merge develop
# → 出现冲突提示

# 查看冲突文件
git status

# 手动编辑冲突文件，解决冲突标记
# <<<<<<< HEAD
# =======
# >>>>>>> develop

# 标记为已解决
git add <冲突文件>
git commit -m "解决合并冲突"
git push origin feature/xxx
```

**原则**：如果对冲突解决不确定，**立即在团队群中沟通**，不要强行合并。

### 7.2 版本号规则

采用语义化版本：`v<主版本>.<次版本>.<修订号>`

| 变更类型 | 版本号变化 |
|----------|-----------|
| 重大变更/不向下兼容 | 主版本 +1 |
| 新功能/向下兼容 | 次版本 +1 |
| Bug修复 | 修订号 +1 |

## 八、禁止事项

🚫 **禁止** `git push --force` 到共享分支（main、develop）  
🚫 **禁止** 直接在main或develop分支上提交代码  
🚫 **禁止** 提交包含密码、Token、密钥的代码  
🚫 **禁止** 提交编译产物（.class、node_modules、dist等）  
🚫 **禁止** 提交IDE个人配置文件（.idea、.vscode等，除EditorConfig外）
