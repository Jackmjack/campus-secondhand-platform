## 三、表结构详细设计

### 3.1 用户表 (user)

```sql
CREATE TABLE `user` (
    `id`            BIGINT        NOT NULL AUTO_INCREMENT COMMENT '用户ID',
    `student_id`    VARCHAR(20)   NOT NULL COMMENT '学号/工号',
    `username`      VARCHAR(50)   NOT NULL COMMENT '用户名（学号/工号，用于登录）',
    `password_hash` VARCHAR(255)  NOT NULL COMMENT '密码哈希（BCrypt加密）',
    `nickname`      VARCHAR(50)   DEFAULT NULL COMMENT '昵称（默认使用真实姓名）',
    `real_name`     VARCHAR(50)   DEFAULT NULL COMMENT '真实姓名（注册时填写）',
    `avatar_url`    VARCHAR(255)  DEFAULT NULL COMMENT '头像URL',
    `phone`         VARCHAR(20)   DEFAULT NULL COMMENT '手机号（加密存储）',
    `email`         VARCHAR(100)  DEFAULT NULL COMMENT '邮箱',
    `department`    VARCHAR(100)  DEFAULT NULL COMMENT '院系',
    `major`         VARCHAR(100)  DEFAULT NULL COMMENT '专业',
    `grade`         VARCHAR(20)   DEFAULT NULL COMMENT '年级（如2024级）',
    `role`          VARCHAR(20)   NOT NULL DEFAULT 'USER' COMMENT '角色: USER/ADMIN',
    `status`        TINYINT(1)    NOT NULL DEFAULT 1 COMMENT '状态: 1正常 0禁用',
    `last_login_at` DATETIME      DEFAULT NULL COMMENT '最后登录时间',
    `created_at`    DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `updated_at`    DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    `is_deleted`    TINYINT(1)    NOT NULL DEFAULT 0 COMMENT '逻辑删除: 0未删除 1已删除',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_user_student_id` (`student_id`),
    UNIQUE KEY `uk_user_username` (`username`),
    KEY `idx_user_department` (`department`),
    KEY `idx_user_status` (`status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';
```

### 4.2 索引使用原则

1. **最左前缀原则**：联合索引按查询频率排列字段顺序
2. **避免过多索引**：每个表索引数控制在5个以内
3. **覆盖索引优先**：常用查询尽量使用覆盖索引减少回表
4. **定期分析**：使用`EXPLAIN`分析慢查询，根据实际数据调整索引

## 八、事务隔离与并发锁设计规范

### 8.1 事务隔离级别设定
*   系统统一采用 MySQL InnoDB 默认的 **Repeatable Read (可重复读，简称 RR)** 隔离级别。
*   通过 MVCC 快照读提升 `SELECT` 检索的吞吐率，避免读取操作与写操作的相互阻塞。

### 8.2 并发锁应用规范
为了防范超卖、并发数据丢失和死锁，系统应遵循以下加锁准则：

#### 8.2.1 悲观锁使用（当前读）
*   **适用场景**：商品下单占用、租赁时段锁定、以物换物提议确认。
*   **要求**：必须在 `@Transactional` 本地事务中，对查询主句使用 `FOR UPDATE`。
    ```sql
    -- 执行锁定当前读，获取行锁，并发状态更新
    SELECT * FROM product WHERE id = ? FOR UPDATE;
    ```
*   在 RR 隔离级别下，利用 Next-Key Lock 机制排他，防范幻读产生的状态二次写。

#### 8.2.2 乐观锁使用（版本对比）
*   **适用场景**：用户信用分变更、商品点击浏览计数、拼卡加入人数更新。
*   **要求**：
    1.  更新 SQL 必须比对 `version` 字段且递增：`SET version = version + 1 WHERE id = ? AND version = ?`。
    2.  若影响行数返回为 `0`，说明遭遇并发竞争，Java 端应当实施自适应自旋（重新读取数据 -> 重新计算 -> 再次尝试更新，建议最高自旋 3 次），直至成功。

#### 8.2.3 联合锁与防死锁规范
*   **适用场景**：以物换物（需要同时加锁两件商品记录）。
*   **要求**：
    1.  **升序排序**：对需要加锁的记录 ID 组进行升序排序，以严格相同的顺序请求 `FOR UPDATE`（例如先锁小 ID，再锁大 ID），消除死锁的环路等待特征。
    2.  **分布式多资源锁**：对于跨进程协作场景，使用 Redisson 的 `getMultiLock` 联合加锁，并设置锁自动过期释放。
