## 一、设计目标与原则

### 1.1 设计目标

| 目标 | 说明 |
|------|------|
| **前后端分离** | 后端提供RESTful API，前端独立开发部署，通过HTTP JSON通信 |
| **高内聚低耦合** | 模块间通过接口交互，每个模块内部高度自治 |
| **可扩展性** | 架构设计支持AI推荐服务独立部署，预留第二阶段的区块链/IM/拼团/小法庭模块接入点 |
| **安全优先** | 认证、授权、数据加密在架构层面保障 |

### 1.2 设计原则

- **单一职责**：每个服务/模块只做一件事
- **接口隔离**：前端只依赖接口契约，不关心后端实现
- **依赖倒置**：Service层面向接口编程
- **契约优先**：先定义API，再实现前后端

### 4.11 并发安全与锁控制流程

#### 4.11.1 当前读悲观锁防幻读/超卖（如租赁与交易下单）
```
买家/租客发起下单请求 → 开启 @Transactional 事务
     │
     └── 执行锁定读：SELECT * FROM product WHERE id = #{id} FOR UPDATE;
              │
              ├── 触发 InnoDB 的 Next-Key Lock (锁住记录与间隙，防并发幻读)
              └── 获取行锁 → 判断状态是否为 ACTIVE / AVAILABLE
                       ├── 状态符合 → 执行状态更新为 RESERVED / RENTED → 提交事务释放锁
                       └── 状态不符 → 抛出业务异常自动回滚事务释放锁
```

#### 4.11.2 多版本自适应乐观锁更新（如信用分变动）

## 六、关键设计决策

### 6.1 为什么选择Monorepo单仓？

- 4人团队规模小，多仓管理成本高
- 前后端接口类型可共享（packages/api-types）
- 统一的CI/CD流水线
- 一次`git pull`获取全部代码

### 6.2 为什么初期不做在线支付？

- 对接支付接口需要企业资质（营业执照等）
- 学生团队初期面交模式足够的
- 降低MVP复杂度，后期可接入微信支付/支付宝

### 6.3 为什么AI估价用规则而不是ML模型？

- MVP阶段无历史交易数据训练模型
- 基于规则的估价已能满足70%的需求
- 预留数据采集接口，为后期ML模型做准备

### 6.4 为什么AI推荐使用独立Python服务而不是Java内置？

- Python拥有最成熟的推荐算法生态（scikit-learn、surprise、TensorFlow）
- 独立服务可单独扩展、单独部署，不影响主业务
- 通过HTTP REST通信，与后端解耦
- 初期数据量小可用简单的协同过滤，后期可无缝升级到深度学习模型
